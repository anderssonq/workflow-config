# Frontier

**Audience:** deciding what to build after the backlog, or judging whether an ambitious idea
belongs here.

This is not a backlog and not a wish list. Every entry names a problem the project is
unusually well placed to attack, and a milestone that could **prove it wrong**.

## When NOT to use this skill

- Work that is already decided and scheduled → the issue tracker.
- A design that was considered and rejected →
  [`failure-archaeology`](../failure-archaeology/SKILL.md), Part 2.
- Whether a change is allowed → [`architecture-contract`](../architecture-contract/SKILL.md).

## The entries

```markdown
### F1 — <the problem, stated as a problem and not as a feature>

**Why here:** the asset this project already has that makes it the right place to try.
**Blockers:** what is actually in the way, named. Not "time".
**Falsifiable milestone:** the specific observation that would show this works — or that
it does not. A milestone you cannot fail is not one.
**Status:** unstarted / probing / adopted / retired, with a date.
```

## Positioning discipline

- An entry stops being a frontier the moment it ships. Move it out; do not let this file
  become a changelog of wins.
- An entry that has been "probing" for two quarters with no observation recorded is retired,
  with the reason. That is not failure — an unretired dead idea crowds out a live one.
- **Never write a frontier entry as marketing.** Nobody outside reads this file, and the
  moment it is written to impress, it stops being useful to the person deciding.
